# Shared-theme audit — 2026-10-27

Audited baseline: `3ea78b1`, parent `1.0.0-rc.1`, catalog plugin `0.3.0`. This is a research and prioritization report; the changes recommended below are **not implemented by this audit**.

Subsequent implementation: **rc.2 / plugin 0.4.0** implements the shared work from this backlog. The findings below describe the audited baseline; see [COMPLETION.md](COMPLETION.md) and [VALIDATION.md](VALIDATION.md) for current behavior, actual test outcomes and remaining host/store/device gates.

## Assessment

The six agreed feature areas have a working shared foundation. Rebuilding the theme or adding many plugins is unnecessary. However, functional coverage does not mean that every interaction is polished or that the shops are ready for production. This audit identified shared improvements as well as the hosting and real-data gates already recorded in [COMPLETION.md](COMPLETION.md).

Finish accessibility and catalog selection feedback first. Then improve the reusable merchandising controls and editor experience. Currency/schema, payments and hosted performance must pass before launch. Keep individual hero compositions, glass effects, photography, palettes and brand artwork in child themes.

## Evidence and limits

- Read the parent templates, CSS/JS, catalog plugin, CI configuration and existing functional tests. Previous passing tests remain historical evidence; the complete suite was not rerun for this documentation-only audit.
- A source scan found no missing messages in the theme's Persian JSON catalog for the direct gettext calls examined. The catalog plugin has no bundled Persian catalog or custom translation loader; its custom admin labels remain English. This does not imply that native WordPress/WooCommerce labels are untranslated.
- Re-ran the asset budget: custom CSS **8.15 KB gzip**, custom JS **2.05 KB gzip**. This excludes WordPress, WooCommerce, media, fonts and other extensions; it is not a page-speed result.
- Viewed the local shop at **428×712** and **1366×768**. Neither measured viewport had horizontal document overflow. The four-column desktop cards were approximately **424.6px** high and aligned within rows. At 428px, a row containing a sale product was taller than earlier rows; sale/long-price combinations deserve a focused compact-card review.
- The desktop catalog's first product row began around **568px** from the viewport top. At 428px it began around **618px**. Category navigation and filter controls consume substantial space before products. This is a layout observation, not evidence of a conversion problem.
- Opened the actual price filter. Its rail retained `rgb(53, 34, 76)` and the familiar purple WooCommerce range styling. Both handles were focusable `SPAN` elements with `tabindex="0"`, but no `role`, accessible label, `aria-valuenow`, `aria-valuemin` or `aria-valuemax` in the inspected DOM.
- Browser navigation and a separate localhost HTTP request intermittently timed out. A later product-page attempt also timed out. This was a partial shop review, not a fresh full-site accessibility, browser-compatibility or performance certification. Temporary viewport overrides were reset.
- Read current primary guidance from W3C, WooCommerce, WordPress and Google, plus Baymard's published UX research and specialist storefronts. No competitor speed, accessibility or conversion score was measured.

## Currency/schema finding

Google requires an ISO 4217 code for an offer's `priceCurrency`. The official [SIX current currency XML](https://www.six-group.com/dam/download/financial-information/data-center/iso-currrency/lists/list-one.xml), fetched during this audit with publication date **2026-09-17**, contains `IRR` for Iranian Rial and no `IRT` entry. The [SIX standards page](https://www.six-group.com/en/products-services/financial-information/market-reference-data/data-standards.html) identifies it as the ISO 4217 maintenance agency.

Installed WooCommerce source (`includes/class-wc-structured-data.php`) obtains the store currency and uses it in product offers; the repository has no currency-schema adapter. Therefore IRT offer output is a concrete **integration risk**, inferred from source and configuration, not a newly validated rendered product page. An installed currency/SEO extension could change the eventual output.

The site should still display and store the approved toman prices. Agree one external integration that serializes the appropriate supported currency and its matching numerical amount for schema/feeds, and separately verify the gateway's expected units. Merely replacing `IRT` with `IRR` is incorrect. Do not multiply product prices in the theme, change existing orders, or apply a second conversion in another extension. Validate all nested offer/variation/shipping monetary fields with the chosen stack; correct markup does not guarantee a particular Google search appearance or regional eligibility. [Google currency requirement](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing).

## Final verification matrix

- **Layouts:** home, shop, parent/leaf category, brand directory/archive, search/no results, simple/variable/sale/unpriced/unavailable product, article/archive, support, cart/empty cart, checkout errors, account/recovery and tracking/receipt. Include missing images, very long Persian titles, large prices and unavailable variants.
- **Interaction/accessibility:** keyboard-only navigation, visible focus under the compact sticky header, product tabs/gallery, suggestion panel, filter removal, comparison scrolling, 200% text zoom and 320 CSS-pixel reflow/400% browser zoom as applicable. Check real Safari/iOS and Android as well as desktop Chrome. Inspect reduced motion and contrast in every child palette. [W3C reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html).
- **Commerce:** guest and account checkout, real address/shipping choices, Zarinpal plugin compatibility with the selected classic or block checkout, success/pending/failure/cancel/retry/duplicate callbacks, accurate units, stock restoration/refunds, actual mail delivery and complete recovery/login. Use gateway sandbox/authorized test orders. [Woo payment integration](https://developer.woocommerce.com/docs/block-development/extensible-blocks/cart-and-checkout-blocks/checkout-payment-methods/payment-method-integration/), [account settings](https://woocommerce.com/document/configuring-woocommerce-settings/accounts-and-privacy/).
- **Performance/operations:** real imagery with responsive sizes and compression, host/CDN caching and cart exclusions, two customer sessions, MySQL queries/search load, HTTPS and backup restore. Target field LCP ≤2.5s, INP ≤200ms and CLS ≤0.1 at the 75th percentile; lab measurements help before launch, while field data needs sufficient traffic. [Core Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds).
- **Store content:** real stock/SKUs/pack sizes/specifications, evidence-backed compatibility, contact/social links and owner-approved delivery/returns/warranty/privacy copy. Help templates and a footer About paragraph already exist; they need real information, not fabricated reassurance badges.

## Useful later options

After the shared fixes, consider a shopper-managed comparison shortlist, optional mobile purchase shortcut for long product pages, recently viewed products, wishlists/back-in-stock alerts, reorder shortcuts and consent-aware analytics. Each needs a clear business purpose and, where relevant, a provider/privacy decision. None is necessary just to call the shared foundation useful.

The current [Killer Ink cartridge catalog](https://www.killerinktattoo.co.uk/tattoo-cartridges) separates configuration and brand routes. [LashBase's tweezer collection](https://lashbase.co.uk/collections/tweezers) sits within separate lash/adhesive/tool families. Our inference is to keep category-specific buying attributes and routing, rather than imposing one taxonomy on the three shops. These are content/navigation observations, not designs to copy or proof that their features improve these shops' sales.

Keep automatic dark mode, autoplay sliders, decorative brand effects and heavy page builders out of the parent. Finish items 1–4 first, then 5–8, and repeat release QA before the three child-theme launches.
