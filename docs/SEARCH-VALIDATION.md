# Search lifecycle and integration validation

Search remains a small normalized metadata index, not a full-text engine. Product title, excerpt, body, SKU, aliases, assigned brands and published variation SKUs are normalized on save. Native WordPress post insertion/update and relevant metadata imports also refresh the document. Variation saves, status changes, trash/restore and permanent deletion refresh the parent after WooCommerce child transients are cleared. A per-product reentrancy guard prevents nested save callbacks from indexing the same product recursively.

Categories and brands now have `_wpmain_search_document` term metadata. Term names and confirmed brand aliases are normalized on create/edit; alias metadata changes update their term document and queue assigned-product recovery. Suggestions use WordPress's prepared `WP_Term_Query` meta `LIKE` filtering, returning at most three populated matching terms from the full indexed taxonomy. They no longer inspect only the first 100 terms. Native term visibility/count rules still apply.

Index version 2 queues an upgrade rebuild for existing data. Each batch visits at most 50 products and 50 category/brand terms using ID cursors. WordPress cron or WooCommerce → Search index processes batches; cron-disabled stores must explicitly complete the rebuild there. Old term suggestions may be absent until the upgrade rebuild finishes. “Rebuild search index” also recovers missing documents after imports. Direct SQL changes bypass WordPress hooks and require a rebuild.

Matching still uses substring `LIKE` against metadata; returning six products/three terms bounds result size, not database scan cost. The isolated fixture's 106 populated categories test correctness beyond the former cap, not production capacity or latency. No production catalog size, concurrency, MySQL query cost or host performance claim follows from it. Benchmark intended inventory/search traffic on the actual MySQL host before adding caching, a dedicated index or another engine. Do not restore nested SQL `REPLACE` normalization.

## Repeatable integration run

`node scripts/run-preview-suite.mjs --isolated` boots a fresh database in a unique ignored `.local/ci-site-*` directory, with explicit `/wordpress` mounting so Playground cannot reuse a managed site. It refuses an occupied port 9400 and never resumes `.local/site`. The runtime pins WordPress 7.1.3, WooCommerce 11.2.1, PHP 8.3 and the existing Playground CLI 3.1.40. Six PHP workers support WooCommerce loopbacks; test scripts run sequentially.

The runner requires an explicit success marker written only after every booted lifecycle assertion finishes. The run installs an unconditional mail-capture MU plugin before commerce fixtures. A guarded PHP integration fixture requires both the isolated-CI constant and the fictional demo identity; it verifies captured mail before any checkout or recovery tests. It creates and removes synthetic product/term records to check variation save/private/trash/restore/delete behavior, native post/meta imports, term rename, >100-category matching, rebuild recovery and bundled Persian plugin loading.

`node scripts/run-preview-suite.mjs --isolated --fixtures-only` runs just fresh setup and those booted PHP assertions on port 9401, then disposes the server. It also refuses an occupied port. Full mode continues with the existing HTTP layout, catalog, search, cart, recovery and fictional COD order suites. Readiness has a 120-second bound, each child a 240-second bound, and the overall process a 15-minute watchdog. Fictional email uses `.invalid`; there are no real credentials, gateways or customer records. Test databases and captured mail/orders remain ignored and must never be deployed.

The Linux GitHub Actions integration job always uploads the runner output and available WordPress debug logs, including failed runs. It does not upload fixture databases, orders or captured mail. The offline PHP contracts, JavaScript units, translation coverage/freshness check and syntax checks remain independent checks.

Browser keyboard/screen-reader/RTL/mobile review, real MySQL scale and cache behavior, real mail delivery and authorized payment callbacks remain release gates. Passing HTTP or synthetic lifecycle checks does not certify those gates. Record actual commands/results in the release report; CI configuration alone is not evidence that a remote workflow passed.
